# Deploy (Render + Neon)

Free hosting for this monorepo: **Render** (API web service + static frontend) and **Neon** (Postgres). GitHub Actions runs CI; Render auto-deploys **`master`**.

Local development is unchanged: SQLite (`backend/db.sqlite`) and `npm start`.

## What is free vs what is not

| Piece | Choice | Notes |
|-------|--------|--------|
| Frontend | Render static site | Free CDN, HTTPS, `*.onrender.com` |
| Backend | Render web service (`plan: free`) | Sleeps after ~15 minutes idle; cold start ~1 minute. **750 instance hours / month** |
| Database | [Neon](https://neon.tech) Free Postgres | Durable (unlike SQLite on Render’s ephemeral disk). Render’s own free Postgres **expires after 30 days** — do not use it |
| CI | GitHub Actions | Tests + production build on PR/push to `develop` and `master` |
| CD | Render Blueprint (`render.yaml`) | Deploy on each commit to `master` |
| Custom domain | Later | Attach CNAME on Render when you want a subdomain |

Schedule **jobs** stay in-process (`setInterval` every 2s). They run only while the API instance is awake (user-triggered generate is fine). Render Cron Jobs are paid — not used.

## One-time setup

1. Create a [Neon](https://console.neon.tech) project. Copy the connection string (`postgresql://…?sslmode=require`).
2. Create a [Render](https://dashboard.render.com) account and connect GitHub repo `ZaytsevAndrey/AI_Calendar`.
3. **New → Blueprint** and select this repo (uses root `render.yaml`). Confirm branch **`master`**.
4. When prompted, paste:
   - `DATABASE_URL` — Neon URL
   - `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`
   - `GOOGLE_REDIRECT_URI` — `https://<ai-calendar-api-host>/google-calendar/callback`
5. After the first deploy, copy the two public URLs (API and static site). In [Google Cloud Console](https://console.cloud.google.com/apis/credentials):
   - Authorized **JavaScript origins**: frontend URL
   - Authorized **redirect URI**: exact `GOOGLE_REDIRECT_URI`
6. If the frontend was built before the API URL existed, **Manual Deploy → Clear build cache & deploy** the static site once.

`FRONTEND_URL` and `REACT_APP_API_BASE_URL` are wired in `render.yaml` from each service’s `RENDER_EXTERNAL_URL`.

## Two frontends

The API service stays the Render web service. There are two static sites:

| Site | Hostname | `REACT_APP_API_BASE_URL` | Voice text / speech |
|------|----------|--------------------------|---------------------|
| `ai-calendar-web` | `https://ai-calendar-web-o81n.onrender.com` | Render API, wired in the blueprint | Groq on the Render API, browser voice |
| `ai-calendar-web-home` | assigned when the blueprint is synced | Dashboard value: public origin of the home API | Ollama on the home machine. Azure Speech when the key is set, otherwise Piper |

GitHub Actions builds both bundles on every pull request and push (`frontend-sites` in `.github/workflows/ci.yml`). The home build uses the repository variable `LOCAL_API_PUBLIC_URL` when it is set. Render is what publishes each bundle to its `onrender.com` hostname after a push to `master`.

The home API is this repo's backend on the PC (`LLM_BASE_URL`, `PIPER_URL`, `npm run start:piper`). Its `FRONTEND_URL` is the home site origin, and `GOOGLE_REDIRECT_URI` is `https://<home-api>/google-calendar/callback`. Do not point the existing site at the home API.

## Landing + app on one domain

The static service `ai-calendar-web` serves two independent builds: the Next.js landing (`landing/`) owns `/` and
`/uk/`, the React app owns every other path. `npm run build:site` builds both and `scripts/assemble-site.mjs` merges
them into `site/` (the app's `index.html` becomes `app.html`). Render serves existing files first, then
`/uk` → `/uk/`, then rewrites everything else to `/app.html`.

Visitors with `access_token` in `localStorage` are sent from `/` to `/calendar` before the landing paints; the app's
`/login` clears tokens and sends signed-out visitors to `/`. Details and a routing table: [landing/README.md](../landing/README.md).

| Variable (static site build) | Value |
|------------------------------|-------|
| `REACT_APP_LANDING_URL` | `/` (empty keeps the old in-app sign-in form) |
| `NEXT_PUBLIC_API_BASE_URL` | API URL |
| `NEXT_PUBLIC_SITE_URL` | Public origin of the site; switch to the custom domain when attached |

The API, CORS and Google OAuth settings do not change: everything the browser loads still comes from `FRONTEND_URL`.
Check the combined site locally with `npm run build:site && npm run preview:site` (http://localhost:4000).

## Database migrations

Postgres schema comes from versioned TypeORM migrations in `backend/src/database/migrations/`, run on every boot before the API listens (each migration in its own transaction; `TYPEORM_MIGRATIONS=false` skips them). Since AUD-026 they run under the Postgres advisory lock `luefy:migrations` (`src/database/migration-lock.ts`): instances booting at once migrate one after another, and the next finds nothing to do. A crashed booting instance releases the lock with its connection. `TYPEORM_SYNC` is `false` in `render.yaml`; `synchronize` runs on Postgres only when `TYPEORM_SYNC=true` is set explicitly (throwaway databases). Local SQLite still synchronizes.

Render: `buildCommand` runs `npm run build:backend` (`nest build` → `backend/dist/main.js` and `backend/dist/database/migrations/*.js`); `startCommand` runs `node dist/main`, which connects, runs pending migrations, then serves. A failed migration stops the boot (the previous deploy keeps serving).

| Migration | What it does |
|-----------|--------------|
| `1761750000000-Baseline` | Full schema, generated from the entities on an empty Postgres (`src/scripts/generate-baseline-migration.ts`). On a database that already has `tasks` (made by the old `TYPEORM_SYNC`) it is recorded without running. |
| `1761760000000-SchedulingQueueAndOccurrenceIdentity` | Idempotent `ADD COLUMN IF NOT EXISTS`: `tasks.originalOccurrenceYmd`, `schedule_jobs.attempts / nextRunAt / leaseUntil` + index. Backfills the day of parked series copies from `problematicDay` (seated copies stay null: ambiguous). Fails jobs left `running` without a lease by the old in-process runner. |
| `1761770000000-GoogleWriteQueueLifecycle` | Idempotent: `pending_google_writes.status / nextRunAt / leaseUntil / revision` + index (existing rows become `pending`, due now); `tasks.googleInsertEventId`. |
| `1761780000000-CreateRequestIdempotency` | Idempotent: table `request_idempotency` (user, operation, key, body hash, created resource) + unique index `(userId, operation, key)`. Replaces the unreleased `TaskCreateRequestKey` of the same branch (never deployed). |
| `1761790000000-GoogleWriteQueueUniqueness` | AUD-011. Deletes duplicate `pending_google_writes` rows (keeps the most recent of each task upsert / event delete; a queue row means "make Google match now", so a duplicate carries no extra intent), then partial unique indexes `(userId, taskId) WHERE operation = 'upsert'` and `(userId, googleEventId) WHERE operation = 'delete'`. Idempotent. |
| `1761800000000-AdminConsoleSchema` | Added at the merge into `master`: the admin console (`907b9fc`) was built while `master` still used `TYPEORM_SYNC`. Tables `admin_users`, `api_error_logs`, `voice_turn_logs` (with indexes) and `user.isBlocked / sessionsRevokedAt / lastActiveAt`, `IF NOT EXISTS` — a database where synchronize already made them is unchanged. |

All six only add columns, tables and indexes, backfill one column, fail stale queue rows and delete duplicate queue rows; no column is dropped or retyped, no user data is deleted.

**Verified (local Postgres 16, not Neon):** fresh database → six migrations; three instances booting at once on an empty database all come up with each migration run once (`migrations.pg.spec` AUD-026) → no drift against the entities; a database built by `TYPEORM_SYNC` from `master`'s entities with sample rows → the built app (`node dist/main.js`) booted, recorded the baseline, ran the others, no drift, every row kept, the parked copy backfilled, the stale job failed, the queued Google write due; a second boot ran nothing; an interrupted upgrade reruns cleanly (`migrations.pg.spec`).

**Not verified: Neon.** No Neon access was available (no API key, no `neonctl`, no connection string in this environment). Neon is Postgres (16/17) and supports `uuid-ossp`, so no difference is expected, but run this before the first deploy:

1. In the Neon console, create a branch of the production database (it is a copy; the production branch is untouched) and copy its connection string.
2. Locally, from the repo root: `npm run build:backend`, then
   `DATABASE_URL='<branch url>' PORT=3999 node backend/dist/main.js` — wait for "Nest application successfully started", stop it.
3. On the branch: `SELECT name FROM migrations ORDER BY id;` lists the six migrations; spot-check row counts of `tasks`, `scheduled_tasks`, `user` against production.
4. Optional drift check: `PG_TEST_URL='<branch url>' DATABASE_URL='<branch url>'` and open the branch with the entities (`createSchemaBuilder().log()` must be empty), the way `migrations.pg.spec` does.
5. Delete the branch.

**First deploy of this change (existing Neon database):**

1. Back up the database (Neon branch or `pg_dump`).
2. Deploy with `TYPEORM_SYNC=false` (already in `render.yaml`; check the dashboard value too — a dashboard value overrides the Blueprint).
3. On boot the backend runs the migrations; the log shows the TypeORM migration lines, and `SELECT name FROM migrations` lists all six.
4. If a deploy is interrupted, simply redeploy: the migrations are safe to rerun (`IF NOT EXISTS`).

**Every later entity change needs a migration.** Generate the SQL on an empty local Postgres (the same way as the baseline) or write it by hand, keep it idempotent where possible, and run `npm run test:pg` (CI runs it): `src/database/migrations.pg.spec.ts` fails when migrations no longer produce exactly the entity schema (fresh database and upgrade from the pre-migration schema).

Local Postgres for these checks:

```bash
docker run -d --name luefy-pg-test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=luefy -p 55432:5432 postgres:16-alpine
cd backend
PG_TEST_URL=postgres://postgres:test@localhost:55432/luefy DATABASE_URL=postgres://postgres:test@localhost:55432/luefy npm run test:pg
```

**Rollback.** Code: redeploy the previous commit in Render. The added columns are ignored by older code (all nullable or defaulted), so the schema can stay; this is the safe path. Schema, only if really needed: each migration has `down()` (newest first); `down()` of the last three drops their columns (data in them is lost: request keys, insert ids, Google queue state, copy identity, job retry state). The baseline `down()` drops every table — never run it on production. Restoring the Neon backup branch is the full rollback.

## Custom domain (optional, later)

On Render: each service → **Custom Domains** → add e.g. `calendar.yourdomain.com` (static) and `api.yourdomain.com` (API). At your DNS host, CNAME those names to the `onrender.com` hostnames Render shows. Then update Google OAuth URIs and trigger a frontend rebuild so `REACT_APP_API_BASE_URL` stays correct (or set it explicitly).

## Limits to expect

- First request after idle: API cold start.
- Free instance hours exhausted: API suspends until next calendar month.
- Neon Free: storage and compute quotas; compute scales to zero when idle (next API request waits on DB wake-up too).
- Do not rely on files written next to the API process — the disk is not persistent. All app data must live in Postgres.

## Copy local SQLite into Neon

Run this **on your machine** (Render does not have `db.sqlite`). It wipes production tables, then copies current product tables. Leftover local-only tables (`categories`, `migrations`, `schedule_undo_snapshots`) are skipped.

From `backend/` (PowerShell):

```powershell
$env:PROD_DATABASE_URL="postgresql://USER:PASSWORD@HOST/neondb?sslmode=require"
$env:CONFIRM_OVERWRITE="yes"
npm run copy-db:prod
```

From `backend/` (Command Prompt / cmd.exe):

```bat
set PROD_DATABASE_URL=postgresql://USER:PASSWORD@HOST/neondb?sslmode=require
set CONFIRM_OVERWRITE=yes
npm run copy-db:prod
```

`PROD_DATABASE_URL` is the same Neon string as Render `DATABASE_URL`. After the copy, sign in again on the deployed site: production `JWT_SECRET` is not the local one. Google Calendar tokens on the user row are copied, so an existing Google connection should still work once you log in.
