# Deploy (Render + Neon)

Free hosting for this monorepo: **Render** (API web service + static frontend) and **Neon** (Postgres). GitHub Actions runs CI; Render auto-deploys **`master`**.

Local development is unchanged: SQLite (`backend/db.sqlite`) and `npm start`.

## What is free vs what is not

| Piece | Choice | Notes |
|-------|--------|--------|
| Frontend | Render static site | Free CDN, HTTPS, `*.onrender.com` |
| Backend | Render web service (`plan: free`) | Sleeps after ~15 minutes idle; cold start ~1 minute. **750 instance hours / month** |
| Database | [Neon](https://neon.tech) Free Postgres | Durable (unlike SQLite on Render’s ephemeral disk). Render’s own free Postgres **expires after 30 days** — do not use it |
| CI | GitHub Actions | Tests + production build on PR/push to `develop` and `master` |
| CD | Render Blueprint (`render.yaml`) | Deploy on each commit to `master` |
| Custom domain | Later | Attach CNAME on Render when you want a subdomain |

Schedule **jobs** stay in-process (`setInterval` every 2s). They run only while the API instance is awake (user-triggered generate is fine). Render Cron Jobs are paid — not used.

## One-time setup

1. Create a [Neon](https://console.neon.tech) project. Copy the connection string (`postgresql://…?sslmode=require`).
2. Create a [Render](https://dashboard.render.com) account and connect GitHub repo `ZaytsevAndrey/AI_Calendar`.
3. **New → Blueprint** and select this repo (uses root `render.yaml`). Confirm branch **`master`**.
4. When prompted, paste:
   - `DATABASE_URL` — Neon URL
   - `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`
   - `GOOGLE_REDIRECT_URI` — `https://<ai-calendar-api-host>/google-calendar/callback`
5. After the first deploy, copy the two public URLs (API and static site). In [Google Cloud Console](https://console.cloud.google.com/apis/credentials):
   - Authorized **JavaScript origins**: frontend URL
   - Authorized **redirect URI**: exact `GOOGLE_REDIRECT_URI`
6. If the frontend was built before the API URL existed, **Manual Deploy → Clear build cache & deploy** the static site once.

`FRONTEND_URL` and `REACT_APP_API_BASE_URL` are wired in `render.yaml` from each service’s `RENDER_EXTERNAL_URL`.

## Two frontends

The API service stays the Render web service. There are two static sites:

| Site | Hostname | `REACT_APP_API_BASE_URL` | Voice text / speech |
|------|----------|--------------------------|---------------------|
| `ai-calendar-web` | `https://ai-calendar-web-o81n.onrender.com` | Render API, wired in the blueprint | Groq on the Render API, browser voice |
| `ai-calendar-web-home` | assigned when the blueprint is synced | Dashboard value: public origin of the home API | Ollama on the home machine. Azure Speech when the key is set, otherwise Piper |

GitHub Actions builds both bundles on every pull request and push (`frontend-sites` in `.github/workflows/ci.yml`). The home build uses the repository variable `LOCAL_API_PUBLIC_URL` when it is set. Render is what publishes each bundle to its `onrender.com` hostname after a push to `master`.

The home API is this repo's backend on the PC (`LLM_BASE_URL`, `PIPER_URL`, `npm run start:piper`). Its `FRONTEND_URL` is the home site origin, and `GOOGLE_REDIRECT_URI` is `https://<home-api>/google-calendar/callback`. Do not point the existing site at the home API.

## Database migrations

Postgres schema comes from versioned TypeORM migrations in `backend/src/database/migrations/`, run on every boot (`migrationsRun`; each migration in its own transaction). `TYPEORM_SYNC` is `false` in `render.yaml`; `synchronize` runs on Postgres only when `TYPEORM_SYNC=true` is set explicitly (throwaway databases). Local SQLite still synchronizes.

| Migration | What it does |
|-----------|--------------|
| `1761750000000-Baseline` | Full schema, generated from the entities on an empty Postgres (`src/scripts/generate-baseline-migration.ts`). On a database that already has `tasks` (made by the old `TYPEORM_SYNC`) it is recorded without running. |
| `1761760000000-SchedulingQueueAndOccurrenceIdentity` | Idempotent `ADD COLUMN IF NOT EXISTS`: `tasks.originalOccurrenceYmd`, `schedule_jobs.attempts / nextRunAt / leaseUntil` + index. Backfills the day of parked series copies from `problematicDay` (seated copies stay null: ambiguous). Fails jobs left `running` without a lease by the old in-process runner. |

**First deploy of this change (existing Neon database):**

1. Back up the database (Neon branch or `pg_dump`).
2. Deploy with `TYPEORM_SYNC=false` (already in `render.yaml`; check the dashboard value too — a dashboard value overrides the Blueprint).
3. On boot the backend runs the two migrations; the log shows the TypeORM migration lines, and `SELECT name FROM migrations` lists both.
4. If a deploy is interrupted, simply redeploy: both migrations are safe to rerun (the second is all `IF NOT EXISTS`).

**Every later entity change needs a migration.** Generate the SQL on an empty local Postgres (the same way as the baseline) or write it by hand, keep it idempotent where possible, and run `npm test` with `PG_TEST_URL` set: `src/database/migrations.pg.spec.ts` fails when migrations no longer produce exactly the entity schema (fresh database and upgrade from the pre-migration schema).

Local Postgres for these checks:

```bash
docker run -d --name luefy-pg-test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=luefy -p 55432:5432 postgres:16-alpine
cd backend
PG_TEST_URL=postgres://postgres:test@localhost:55432/luefy DATABASE_URL=postgres://postgres:test@localhost:55432/luefy npx jest "\.pg\.spec"
```

**Rollback:** each migration has `down()`. The baseline `down()` drops every table — never run it on production. To undo only the second migration, `down()` drops the new columns (their data is lost: copy identity, job retry state).

## Custom domain (optional, later)

On Render: each service → **Custom Domains** → add e.g. `calendar.yourdomain.com` (static) and `api.yourdomain.com` (API). At your DNS host, CNAME those names to the `onrender.com` hostnames Render shows. Then update Google OAuth URIs and trigger a frontend rebuild so `REACT_APP_API_BASE_URL` stays correct (or set it explicitly).

## Limits to expect

- First request after idle: API cold start.
- Free instance hours exhausted: API suspends until next calendar month.
- Neon Free: storage and compute quotas; compute scales to zero when idle (next API request waits on DB wake-up too).
- Do not rely on files written next to the API process — the disk is not persistent. All app data must live in Postgres.

## Copy local SQLite into Neon

Run this **on your machine** (Render does not have `db.sqlite`). It wipes production tables, then copies current product tables. Leftover local-only tables (`categories`, `migrations`, `schedule_undo_snapshots`) are skipped.

From `backend/` (PowerShell):

```powershell
$env:PROD_DATABASE_URL="postgresql://USER:PASSWORD@HOST/neondb?sslmode=require"
$env:CONFIRM_OVERWRITE="yes"
npm run copy-db:prod
```

From `backend/` (Command Prompt / cmd.exe):

```bat
set PROD_DATABASE_URL=postgresql://USER:PASSWORD@HOST/neondb?sslmode=require
set CONFIRM_OVERWRITE=yes
npm run copy-db:prod
```

`PROD_DATABASE_URL` is the same Neon string as Render `DATABASE_URL`. After the copy, sign in again on the deployed site: production `JWT_SECRET` is not the local one. Google Calendar tokens on the user row are copied, so an existing Google connection should still work once you log in.
