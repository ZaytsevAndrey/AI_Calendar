# Task Creation and Event Scheduling Rules

Документ фіксує цільову логіку створення задачі, її вставки в календар та синку з Google Calendar.

## 1) Модель: налаштування, не типи

Поведінку задають **прапорці та поля**. У UI «Flexible / Fixed / Recurring» — лише **пресети**, які заповнюють ці налаштування; після вибору все можна змінити вручну.

| Режим (пресет) | Що сетиться |
|----------------|-------------|
| **Flexible** (дефолт) | не fixed, не recurring, split увімкнено, 30 хв |
| **Fixed** | fixed time, split вимкнено, потрібні старт і кінець |
| **Recurring** | не fixed, recurring Daily, split увімкнено, дні Mon–Fri |

У API/БД для нових записів `eventType` лише **`fixed`** або **`admin`** (усі не-fixed). Старі значення на кшталт `learning` / `daily_routine` читаються як flexible.

## 2) Базові правила створення

- Обов’язкові в UI: **назва**; для non-fixed — **тривалість**; для fixed — **старт і кінець** (end > start).
- День без години (у формі або голосом: «завтра», «в п’ятницю») — **deadline** 23:59 того дня і preferred start з 00:00 того ж дня (flexible). Планувальник не ставить її раніше цього дня. Фіксований слот лише якщо є конкретний час.
- `priority` у формі завжди є (дефолт medium); в API опційний.
- Задача може мати **тільки одну фазу** (`phaseId` / `phaseIds` max 1). Порожня фаза = будь-який час у межах wake/sleep.
- **XOR часу:**
  - Fixed → `scheduledStartTime` + `scheduledEndTime`.
  - Non-fixed → optional **preferred start** (час доби). Якщо задано, кінець = старт + `estimatedTimeInMinutes`; зберігається в тих самих `scheduledStartTime` / `scheduledEndTime`.
- Recurring: `isRecurring` + `recurrencePattern` (`DAILY` / `WEEKLY` / `BIWEEKLY` / `MONTHLY`).
- Optional: `recurrenceWeekDays` (0 = Sunday … 6 = Saturday). Порожньо або всі 7 днів = без додаткового фільтра днів.
- `allowSplit` — лише для non-fixed; фактичний спліт = цей прапорець **і** user setting `allowSplitScheduling`.

## 3) Основний алгоритм вставки задачі в календар

### 3.1 Порядок обробки

1. Спочатку сортуємо задачі за пріоритетом (від higher до lower), далі FIFO.
2. Fixed задачі є якірними: їх не можна рухати.
3. Для інших задач шукаємо найближчий вільний слот.

### 3.2 Вибір слота

- Стратегія: **earliest available** (найближчий вільний слот).
- Слот має бути в межах вікна фази.
- Перетинати межі вікна фази не можна.
- Якщо слот зайнятий higher-priority задачею, виконуємо перебудову (displacement) за поточними правилами рушія.

### 3.3 Якщо не влазить у поточний день

- **Recurring:** якщо occurrence не вміщається в дозволений інтервал/день, переносимо на наступний валідний день; якщо загалом не влазить у горизонт — warning користувачу.
- **Fixed:** не пересуваємо.
- **Flexible:** шукаємо в наступні дні (в рамках горизонту).

### 3.4 Deadline

- Якщо задача не влазить до дедлайну, формуємо warning:
  - рекомендуємо підняти пріоритет або переглянути фазу/тривалість/спліт.

### 3.5 Weekend vs phase

- Якщо є конфлікт між глобальним `weekendWork` і фазою, **фаза має вищий пріоритет**.

## 4) Фаза і часові обмеження

- У задачі лише одна фаза.
- `preferredStartTime` (у UI dropdown) показує слоти по 15 хв:
  - поза інтервалом фази — disabled;
  - в межах фази — enabled.
- Для overnight фаз (наприклад `22:00-06:00`) застосовується логіка вікна з переходом через північ.

## 5) Recurrence та дні тижня

- Підтримуються: `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`.
- Дні задачі (`recurrenceWeekDays`) **перетинаються** з днями фази (`weekDays`). Порожній перетин = немає валідних днів.
- Якщо днів не вибрано — лишається лише обмеження фази (якщо воно є).
- Для `DAILY` / `WEEKLY` / `BIWEEKLY` з обмеженням днів планувальник крокує по днях і пропускає невалідні. `MONTHLY` дні в UI не показує.
- У Google повторювана задача — **одна серія (RRULE, з BYDAY за потреби)** до кінця горизонту. Неповторювані flexible задачі лишаються окремими подіями на кожен слот.

## 6) Split правила

- Split можливий лише для non-fixed і лише якщо і задача, і user settings дозволяють.
- Мінімальний/максимальний chunk визначається налаштуваннями користувача.
- Дефолтний мінімальний chunk: **30 хв**.
- Результат split синкається в календар (не відкидається).

## 7) Sync з Google Calendar

### 7.1 Коли виконується

- Sync тригериться при будь-якому оновленні задачі (CRUD + статусні зміни), через поточний pipeline.
- Для non-fixed після replan обробка job для цього ж користувача запускається одразу.

### 7.2 Загальні правила

- Сервер працює в UTC.
- Клієнт показує час у локалізації користувача.
- Якщо Google не підключено, sync пропускається і логуються warning-и.
- Для поточної ітерації помилки sync показуються через toast.

### 7.3 Статуси задачі

- `completed` / `canceled` не видаляють подію з Google автоматично (подія залишається).

## 8) Edge cases (обов’язкова поведінка)

1. **Recurring + phase Mon–Fri + pattern DAILY** (без своїх днів або з ширшим набором)  
   → входження лише в Mon–Fri.

2. **Recurring + свої дні (напр. Mon, Wed) + фаза Mon–Fri**  
   → входження лише в перетині (Mon, Wed).

3. **Preferred start зайнятий fixed/higher-priority**  
   → шукаємо найближчий валідний слот у межах фази.

4. **У день немає вікна у фазі**  
   → переносимо на наступний валідний день.

5. **Не влазить у горизонт/дедлайн**  
   → не ставимо насильно, формуємо warning.

6. **Overnight phase**  
   → слот рахується з переходом через північ за правилами фазового вікна.

7. **Invalid estimated time (<=0 або некоректне)**  
   → валідація не пропускає створення.
