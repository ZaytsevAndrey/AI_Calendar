# Task Creation and Event Scheduling Rules

Документ фіксує цільову логіку створення задачі, її вставки в календар та синку з Google Calendar.

## 1) Модель: налаштування, не типи

Поведінку задають **вкладка** і поля. Fixed / Flexible / Recurring / Later заповнюють прапорці; чекбоксів Fixed і Recurring у формі немає. Нова задача відкривається на Fixed. Later — задачі, які залишили на потім, коли буде час (API лишається `isUnscheduled`).

| Режим (вкладка) | Що сетиться |
|-----------------|-------------|
| **Fixed** (дефолт) | fixed time, split вимкнено, діапазон днів і годинники на першому та останньому, `deadline` null. Селект **Повтор** (дефолт «Не повторюється») робить fixed-серію: `isRecurring` + патерн/дні, `earliestStartTime` = день першого слота, `deadline` = необовʼязкове «Повторювати до» |
| **Flexible** | не fixed, не recurring, split у даних увімкнено (у формі не показується), 30 хв |
| **Recurring** | не fixed, recurring Daily, дні Mon–Fri |
| **Later** | `isUnscheduled`, без слота, без replan/Google, без deadline |

Перемикання вкладки не губить уже вибране: день вікна Flexible стає днем Fixed (з бажаним початком — готовим слотом тієї ж тривалості), слот Fixed стає вікном, бажаним початком і тривалістю Flexible (для Recurring — лише початком серії), тривалість переживає Flexible ↔ Recurring. Під вкладками — інфоблок «що це за тип і на що впливає» з «Більше не показувати» (per-browser, `localStorage`) і кнопкою сховати; сховати діє лише на свою вкладку. Локація — пікер з підказками OpenStreetMap (`/places/search`), вільний текст теж валідний; на Fixed вона в основній формі, на інших — у More options. Біля полів — `?` з тултіпом.

**Reminder** is not a row in this table. The fifth form segment writes a day reminder (`/day-reminders`), a separate record with a civil day, an optional clock, and an optional repeat. It is not an `eventType`, it is not placed, and it does not become an inbox task.

У API/БД для нових записів `eventType` лише **`fixed`** або **`admin`** (усі не-fixed). Старі значення на кшталт `learning` / `daily_routine` читаються як flexible.

## 2) Базові правила створення

- Обов’язкові в UI: **назва**; для flexible/recurring — **тривалість**; для fixed — **діапазон днів і початок/кінець** (end > start). Вкладка Fixed використовує спільний `DateTimeRangeField`: перший клік дня ставить початок, другий — кінець; годинник початку на першому дні, годинник кінця на останньому, запис `YYYY-MM-DDTHH:mm`. На одному дні порожній кінець бере тривалість за замовчуванням і тримається за початком, доки кінець не змінити окремо. **Later** — лише назва, без дедлайну. Не синкається з Google і не потрапляє в Generate/replan, поки користувач не натисне **Schedule** або не збереже без `isUnscheduled`. Тип задачі задає вкладка форми, не чекбокси Fixed/Recurring. Нова задача відкривається на вкладці Fixed. Клік по дню календаря відкриває Flexible з цим днем у діапазоні.
- Діапазон днів у формі (не нативний datetime) пише **`earliestStartTime`** 00:00 першого дня і **`deadline`** 23:59 останнього у **таймзоні з Settings**. Порожній діапазон — будь-коли. `deadline` тут лише кінець вікна flexible/recurring, не окремий дедлайн. Fixed і Later зберігають `deadline: null`. Планувальник ставить задачу лише в цьому **локальному** дні/діапазоні і **не затирає** `earliestStartTime` після replan. Кілька днів у діапазоні додатково дають `eligibleWeekDays`. Фіксований слот лише якщо є конкретний час.
- Голос: день без годинника, подія на цілий день і вікно, назване лише днем, ідуть від пробудження до сну, не від 00:00 до 23:59. Fixed і Later не отримують `deadline`. Кілька дат, кожна названа один раз, — окремі одноразові справи. Спільний годинник їх не зліплює в серію.
- `priority` у формі в **More options** (дефолт medium; посадка його не враховує); в API опційний. **Статус** показується лише при редагуванні (створення завжди todo): todo, in_progress, completed, canceled.
- Закриття форми з незбереженими змінами питає підтвердження.
- Задача може мати **тільки одну фазу** (`phaseId` / `phaseIds` max 1). Порожня фаза = будь-який час у межах wake/sleep. **Fixed фази не має:** форма її не показує і зберігає `phaseIds: []`.
- **XOR часу:**
  - Fixed → `scheduledStartTime` + `scheduledEndTime`; `estimatedTimeInMinutes` = довжина слота.
  - Non-fixed → optional **preferred start** (час доби). Якщо задано, кінець = старт + `estimatedTimeInMinutes`; зберігається в `scheduledStartTime` / `scheduledEndTime` (після replan це вже поставлений слот). День старту — день уже поставленого слота, якщо він у вікні; інакше перший день вікна; інакше сьогодні. Тож збереження без зміни часу не рухає задачу. Вікно днів — окремі `earliestStartTime` + `deadline`. Без фази список preferred start обмежений wake–sleep.
- Recurring: `isRecurring` + `recurrencePattern` (`DAILY` / `WEEKLY` / `BIWEEKLY` / `MONTHLY`).
- Optional: `recurrenceWeekDays` (0 = Sunday … 6 = Saturday). Порожньо або всі 7 днів = без додаткового фільтра днів.
- `allowSplit` — лише для non-fixed; у формі не показується (функції дроблення в UI ще немає). Фактичний спліт = цей прапорець **і** user setting `allowSplitScheduling`.

### 2.1 Voice create vs form

- **`complete`** (створює одразу): є **назва**. Дефолти ок (30 хв, medium, без фази). День без години дозволений і йде від пробудження до сну. Справа, яка не є подією і не має часу, створюється без часу. Подія без часу — питання коли. Місце саме по собі нічого не вирішує. Fixed без години стає flexible. Повтор без патерну — одноразова задача.
- **`needs_clarification`**: немає назви, час неможливо визначити, або годинник без дня вже минув. Одне питання. Після відповіді більше не питаємо.
- Дати рахуються в IANA з **Settings** (клієнт шле її в `/voice/parse-task`; сервер бере `settings.timeZone`, якщо клієнт порожній).

## 3) Основний алгоритм вставки задачі в календар

**Контракт посадки:** [spec-incremental-placement.md](spec-incremental-placement.md). Інбокси й опції шита: [spec-conflict-rules.md](spec-conflict-rules.md). Нижче — коротке резюме. Живий рушій ще робить повний реплан.

### 3.1 Порядок обробки

1. Важливість = **тип** (fixed / flexible / recurring) + **preferred time**; numeric priority для placement ігнорується (soft-deprecate).
2. Fixed / Google — якорі: їх не рухаємо.
3. Заявлений інтервал поверх уже заседженої flexible: нова сідає, зрушується лише перекрита. Без preferred нова бере найближчу вільну дірку і нікого не зрушує.
4. Preferred точно на fixed / Google / звичку → питати (conflict options). Ланцюжка витіснень немає.

### 3.2 Вибір слота

- Спочатку **preferred**, якщо заданий і вільний; інакше earliest available у фазі.
- Слот у межах вікна фази; межі фази не перетинаємо.
- Немає тихого displacement по priority; overflow / no-reply → Problematic (див. conflict rules).

### 3.3 Якщо не влазить у поточний день

- **Recurring:** день, який не влазить, пропускається; решта серії лишається на своїх місцях. Усі входження до горизонту сідають при створенні. Якщо серія загалом не має жодного дня — **Problematic**.
- **Fixed:** не пересуваємо; fixed vs fixed → завжди питати.
- **Fixed-серія:** кожен день — той самий годинник і довжина першого слота (`estimatedTimeInMinutes` = довжина слота). Перекриту flexible зсуваємо. День, де вже стоїть інша fixed / Google-подія, сусідньої дірки не шукає і паркується як Problematic; решта серії лишається.
- Серія (будь-яка) починається з дня `earliestStartTime`, якщо він ще попереду, інакше з сьогодні.
- **Flexible:** шукаємо в наступні дні (в рамках горизонту); silent relocate у межах фази коли це вона «заважає» після вибору користувача.

### 3.4 Placement window

- `earliestStartTime` — hard «не раніше» (instant у **таймзоні Settings**, не midnight UTC-хоста). Day-only From (локальні **00:00**) snap до wake того локального дня. На Postgres `wakeTime` приходить як `HH:mm:ss` — енджин нормалізує до `HH:mm` (інакше на проді 00:00 падає на «сьогодні», а 00:01 працює).
- `deadline` — кінець вікна flexible/recurring, hard «не пізніше». Окремого дедлайну немає. Fixed і Later пишуть null.
- `eligibleWeekDays` — опційний фільтр днів усередині діапазону (лише non-recurring).
- Якщо задача не влазить у вікно → **Later** (не Problematic); warning без «підняти пріоритет» — фаза / тривалість / спліт / вікно.

### 3.5 Weekend vs phase

- Якщо є конфлікт між глобальним `weekendWork` і фазою, **фаза має вищий пріоритет**.

## 4) Фаза і часові обмеження

- У задачі лише одна фаза.
- `preferredStartTime` (у UI dropdown) показує слоти по 15 хв:
  - поза інтервалом фази — disabled;
  - в межах фази — enabled.
- Для overnight фаз (наприклад `22:00-06:00`) застосовується логіка вікна з переходом через північ.

## 5) Recurrence та дні тижня

- Підтримуються: `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`.
- Дні задачі (`recurrenceWeekDays`) **перетинаються** з днями фази (`weekDays`). Порожній перетин = немає валідних днів.
- Якщо днів не вибрано — лишається лише обмеження фази (якщо воно є).
- Для `DAILY` / `WEEKLY` / `BIWEEKLY` з обмеженням днів планувальник крокує по днях і пропускає невалідні. `MONTHLY` дні в UI не показує; повтор — у число першого повторення (форма показує, яке саме).
- Форма пропонує новій задачі «Щотижня у вибрані дні» (`DAILY` + дні), «Раз на два тижні», «Щомісяця», плюс швидкі «Будні» / «Щодня». `WEEKLY` з днями дає ті самі дні, що й `DAILY`, тому лишається у списку лише для задачі, яка вже його має: переписування патерну рахувалось би зміною розкладу.
- У Google повторювана задача — **одна серія (RRULE, з BYDAY за потреби)** для ще відкритих occurrence. Після replan минулі інстанси лишаються: стара серія capped `UNTIL`, майбутнє — нова серія. Неповторювані flexible задачі лишаються окремими подіями на кожен слот.

## 6) Split правила

- Split можливий лише для non-fixed і лише якщо і задача, і user settings дозволяють.
- Мінімальний/максимальний chunk визначається налаштуваннями користувача.
- Дефолтний мінімальний chunk: **30 хв**.
- Результат split синкається в календар (не відкидається).

## 7) Sync з Google Calendar

### 7.1 Коли виконується

- Які збереження взагалі чіпають слоти: [spec-incremental-placement.md](spec-incremental-placement.md) §5. Косметика, complete, cancel, skip і delete чужі слоти не переписують. Геометрична зміна саджає лише цю задачу і прямих перекритих.
- Живий бекенд досі ставить `full_replan` на більшість збережень гнучкої задачі і відповідає з `jobId`. Це не ціль.
- Unscheduled задачі живуть у секції **Unscheduled** на Tasks: **Done** ховає їх (`completed`), **Schedule** відкриває ту саму форму вже як планувальну. Поки слота немає у flexible-задачі, вона може коротко бути в Calendar strip **Unscheduled**. **Done** лише ставить `completed` і не синкає flexible-задачу в Google. Посадка перед записом слота ще раз читає статус: якщо вже `completed`, слот не пишеться.
- Кнопки Generate / Review у цільовому продукті немає: місце з’являється при створенні. Живий календар ще показує її, доки імплементація цього контракту її не прибере.

### 7.2 Загальні правила

- Сервер працює в UTC.
- Клієнт показує час задачі у **таймзоні Settings** (IANA). Зона браузера на payload не пишеться.
- Якщо Google не підключено, sync пропускається і логуються warning-и.
- Для поточної ітерації помилки sync показуються через toast (червоний, заголовок + деталь з API).
- **Clear і живий replan не чіпають повністю закінчені** app-слоти (`scheduledEndTime <= now`), включно з уже минулим сьогодні. Ціль: майбутнє теж не переписується, крім заявленого інтервалу і прямих перекритих ([spec-incremental-placement.md](spec-incremental-placement.md)). Recurring у Google: стара серія отримує `UNTIL`, нова — лише відкриті occurrence, які цей крок змінив.
- Сірими в календарі стають лише події **нашого** app-календаря, які вже закінчились. Інші Google-календарі лишають свій колір.

### 7.3 Статуси задачі

- `completed` / `canceled` не видаляють уже існуючу подію з Google автоматично.
- **Done** з Unscheduled не створює нову подію: задача просто зникає з інбоксу.

## 8) Edge cases (обов’язкова поведінка)

1. **Recurring + phase Mon–Fri + pattern DAILY** (без своїх днів або з ширшим набором)  
   → входження лише в Mon–Fri.

2. **Recurring + свої дні (напр. Mon, Wed) + фаза Mon–Fri**  
   → входження лише в перетині (Mon, Wed).

3. **Preferred start зайнятий**  
   → див. [spec-incremental-placement.md](spec-incremental-placement.md): заявлений preferred забирає інтервал і зрушує лише перекриту; без preferred — найближча вільна дірка, нікого не зрушуємо; preferred точно на fixed → питати. Priority не вирішує конфлікт.

4. **У день немає вікна у фазі**  
   → переносимо на наступний валідний день.

5. **Не влазить у горизонт/дедлайн**  
   → не ставимо насильно, формуємо warning.

6. **Overnight phase**  
   → слот рахується з переходом через північ за правилами фазового вікна.

7. **Invalid estimated time (<=0 або некоректне)**  
   → валідація не пропускає створення.

## 9) UI toasts

Тости кольорові за типом: **success** зелений, **error** червоний, **warning** жовтий, **info** синій. Формат: короткий **title** і **detail** другим рядком.

Після CRUD задачі:

| Дія | Title | Detail |
|-----|--------|--------|
| Create / voice create | `Task created` | назва · **на коли** (слот, вікно From–Until, Due/From) · тривалість якщо немає точного слота · `Repeats …` |
| Update | `Task updated` | те саме |
| Delete | `Task deleted` | назва |

«На коли» береться з `scheduledStartTime`/`scheduledEndTime`, інакше з `earliestStartTime`+`deadline`. Помилка збереження: title на кшталт `Could not create task`, detail — повідомлення API.

Generate / Clear на Calendar: той самий патерн (success / warning / error + counts).
