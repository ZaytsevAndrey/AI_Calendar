## 1. Фактичний контракт домену

Підсумок брифу в цілому вірний. Уточнення і розбіжності — нижче.

### 1.1 Два незалежні виміри

| Вимір | Поле | Значення |
|---|---|---|
| Рухомість | `eventType` | `fixed` — годинник обрав користувач, двигун не рухає; `admin` — гнучка (у UI «flexible»). `daily_routine`, `quick_win`, `deep_work` — лише в старих рядках, UI трактує їх як гнучкі |
| Повтор | `isRecurring` + `recurrencePattern` (`DAILY`/`WEEKLY`/`BIWEEKLY`/`MONTHLY`) + `recurrenceWeekDays` | Одноразова або серія |

Усі чотири комбінації підтримуються бекендом і покриті `scheduling-invariants.spec.ts`. На фронтенді є спільний класифікатор `taskTraits()` (`modules/tasks/schedulingTraits.ts`), і календар, фільтри та превʼю голосу вже показують обидва виміри окремо.

### 1.2 Що бриф не згадує, але UI має враховувати

1. **Третій стан — «На потім» (`isUnscheduled`)**. Це не рухомість і не повтор, а стан «без слота». Обмеження бекенду: на потім може бути лише гнучка одноразова (`applyUnscheduledConstraints` скидає повтор і забороняє fixed). Тобто комбінацій не 4, а 5: 4 заплановані + «На потім».
2. **Fixed вимагає годинника** (`scheduledStartTime` і `scheduledEndTime`). Fixed без часу не існує. Гнучка може мати бажаний час, і це лише побажання.
3. **Вікно (`earliestStartTime`/`deadline`) означає різне:**
   - одноразова гнучка — жорсткі межі пошуку місця;
   - серія — початок і кінець серії (From — день старту, Until — останній день);
   - fixed-серія — From = день першого слота, Until — «повторювати до».
4. **Ідентичність повторення** — серія + цивільний день. Таблиці повторень немає. Повторення, яке змінили окремо, стає **копією**: окрема неповторювана задача з `seriesGroupId`, `parentSeriesId`, `originalOccurrenceYmd`. Дні з іншим годинником стають **сиблінгом** серії.
5. **Що можна зробити з одним повторенням (бекенд):**

| Операція | Ендпоінт | Обмеження |
|---|---|---|
| Перенести час / змінити тривалість одного дня | `POST /schedule/move-event`, `seriesScope: occurrence` | Лише в межах того самого дня |
| Перенести «цей і наступні» | `move-event`, `seriesScope: series` | Лише час |
| Перенести всю серію | `move-event`, `seriesScope: all` | Лише час |
| Пропустити день | `POST /tasks/:id/skip-occurrence` | Не для fixed одноразової, Later, виконаної |
| Видалити «цей і наступні» | `POST /tasks/:id/end-series-from` | |
| Видалити все | `DELETE /tasks/:id` | Разом із припаркованими копіями |
| Змінити назву, фазу, опис тощо | `PATCH /tasks/:id` | **Завжди вся серія.** Для одного дня — немає |
| Позначити один день виконаним | — | **Немає.** Статус — на всю задачу |

6. **`allowSplit`** зберігається і копіюється, але двигун його не використовує (розбиття не підтримується, §12). Фронтенд шле його, але в UI не показує. Це мертве поле, проблем для користувача немає.

### 1.3 Розбіжність контракту, важлива для UI

**`PATCH /tasks/:id` виводить задачу з групи серії, якщо в тілі є будь-який із `MEMBERSHIP_BREAKING_KEYS` (name, description, eventType, isRecurring, deadline…). Перевіряється наявність ключа, а не зміна значення** (`series-group.util.ts: breaksSeriesMembership`). Форма завжди шле повний payload (`buildTaskPayload`). Тому будь-яке збереження форми копії або сиблінга — навіть коли змінили лише час — назавжди відриває її від серії. Після цього вона не повертається в серію (re-merge), а з календарної картки зникає маркер повтору. **[код]**

## 3. Невідповідності

### 3.1 Підтверджені функціональні несумісності

**F1. Вибір «Лише цей день» / «Цей і наступні» при редагуванні ігнорується.** [код]
`EventPreview` показує для серії кнопку «Редагувати ▾» з трьома варіантами, але `CalendarPage.openEditorFromPreview(_scope)` параметр не використовує й завжди відкриває форму всієї серії. Користувач обрав «лише цей день», змінив час, зберіг — змінилася вся серія. Це найсерйозніша проблема: UI обіцяє одне, а робить інше.

**F2. Перемикання вкладки стирає повтор.** [код]
`presetPatch('fixed')` і `presetPatch('flexible')` ставлять `isRecurring: false`. `presetPatch('recurring')` переписує патерн на `DAILY` + будні. Тому:
- фіксована серія → «Гнучка» = одноразова; щоб зробити гнучку серію, треба йти в «Повторювана»;
- «Повторювана» (гнучка серія «пн, ср») → «Фіксована» = повтор вимкнено, а якщо ввімкнути знову — дні беруться з дня слота;
- фіксована щомісячна серія → «Повторювана» = патерн стає «будні».

Змінити рухомість серії без втрати правила повтору неможливо.

**F3. Збереження форми копії або сиблінга серії відриває їх від серії.** [код] Див. §1.3.

**F4. Зміна правила повтору існуючої серії, ймовірно, не прибирає дні, що вже не підходять.** [перевірити]
Без зміни годинника `placeOptions` дає `commit: 'keep'` + `expandSeries`. `expandSeriesDays` лише **дописує** відсутні дні й не знімає відкриті слоти днів, яких у новому правилі немає (пн–пт → пн, ср: вт і чт лишаються в календарі). Тесту на цей сценарій немає.

**F5. Вимкнення повтору в існуючої серії, ймовірно, лишає слоти кількох днів на одноразовій задачі.** [перевірити]
Шлях `keep` для неповторюваної задачі слоти не чистить, а задача з кількома слотами двигуном не підтримується (§12). Тесту немає.

### 3.2 Неправильний або заплутаний UX

**U1. «Повторювана» — окремий тип поруч із Фіксованою і Гнучкою.** Вкладки: Фіксована · Гнучка · Повторювана · На потім. У «Фіксованій» є селект «Повтор», а в «Гнучкій» його немає. Гнучка серія живе лише у вкладці «Повторювана». Модель асиметрична, а назва «Повторювана: звичка чи рутина» каже, що повторюваною буває лише гнучка задача.

**U2. Поле «Коли» у фіксованої серії одночасно і час, і дата старту серії.** Під час редагування воно показує годинник майстра (перший день серії, часто вже минулий), а не відкрите повторення. Змінити дату в цьому полі = перенести початок серії (`earliestStartTime = fixedSeriesFrom(...)`).

**U3. Поле «Дати» змінює зміст без попередження.** Для одноразової гнучкої це межі пошуку («цього тижня»), для серії — коли серія починається і закінчується. Після перемикання Гнучка → Повторювана вікно «пн–нд цього тижня» тихо стає «серія лише на цей тиждень».

**U4. Тексти `typeInfo` розходяться з доменом:**
- «Повторювана: день, у який не влазить, пропускається» — насправді день стає копією в «Проблемних», а не пропуском;
- «Гнучка: якщо в дати нічого не влазить — потрапляє в “На потім”» — у «На потім» потрапляє лише задача, чиє вікно вже минуло; інакше вона йде в «Проблемні».

**U5. Іконка картки серії ховає рухомість.** `CalendarChipMeta` для члена серії показує лише 🔁 замість 📌 або ↔. Фіксовану серію на сітці не відрізнити від гнучкої (у превʼю це видно).

**U6. Копія серії в превʼю виглядає як звичайна одноразова задача:** немає рядка «Перенесене повторення серії «…», чт 12 листоп.». У фронтенд-типі `TaskDTO` немає поля `originalOccurrenceYmd`.

### 3.3 Можливості бекенду, яких немає в UI

- **M1.** Змінити час або тривалість одного дня (чи «цей і наступні») можна лише перетягуванням у календарі. З превʼю і форми — ніяк (див. F1).
- **M2.** Гнучка серія без годинника (лише фаза і дні) у формі підтримується, а вкладкою «Гнучка» — ні (див. U1).

### 3.4 Обмеження бекенду (не баги UI, нового UI під них не вигадуємо)

- **B1.** Немає зміни назви, фази, опису для одного дня або «цей і наступні». PATCH — завжди вся серія.
- **B2.** Немає «виконано» для одного повторення: Done на серії недоступний (`canCompleteFromPreview`).
- **B3.** Немає перенесення повторення на інший день, лише в межах дня. Обхідний шлях: перенести в межах дня (з'явиться копія), а потім перетягнути копію.
- **B4.** Немає атомарного «цей і наступні — змінити поля». Комбінація `end-series-from` + створення нової серії з клієнта не атомарна.

## 5. Варіанти дизайну

Спільне для всіх варіантів:
- форма лишається модалкою 560 px / шторкою на телефоні;
- чіпи і `filter-chip` з наявної дизайн-системи;
- «Нагадування» лишається окремою кнопкою;
- «Більше опцій» без змін.

### Варіант A — «Режим + Повтор» (мінімальна перебудова вкладок)

Вкладки: **Фіксована · Гнучка · На потім**. «Повторювана» прибрана. В обох запланованих режимах однаковий контрол **Повтор** під полями часу. Перемикання вкладок не чіпає `isRecurring`, патерн і дні.

```
[📌 Фіксована] [↔ Гнучка] [📥 На потім]        [🔔 Нагадування]
Назва *  [___________________________]
+ Опис

── Фіксована ──────────────────────      ── Гнучка ─────────────────────────
Коли *   [чт 12 листоп.  10:00–11:00]     Тривалість  [30] (15)(30)(60)(90)
Місце    [__________]                     Фаза        (Будь-коли)(Ранок)(Робота)
                                           ▸ Уточнити: бажаний час, дати
Повтор   [Не повторюється ▾]              Повтор      [Не повторюється ▾]
  ↳ коли ввімкнено:                         ↳ коли ввімкнено:
  Дні  (пн)(вт)(ср)(чт)(пт)(сб)(нд)         Дні  …  (Будні)(Щодня)
  Починаючи з [12 листоп.]  До [без кінця]  Починаючи з [сьогодні] До [без кінця]
```

- **Типовий стан:** як зараз (Фіксована) або Гнучка — див. §10, П1.
- **Чотири комбінації** = 2 вкладки × «Повтор» вимк./увімк. «На потім» ховає «Повтор» (бекенд не підтримує).
- **Межі серії** («Починаючи з / До») живуть у блоці «Повтор». Для fixed-серії «Коли» означає час першого повторення, а «Починаючи з» за замовчуванням береться з нього (як зараз), але показується окремо (усуває U2, U3).
- **Вікно одноразової гнучкої** («Дати», «Цього тижня…») ховається, коли повтор увімкнено.
- **Швидкість:** «Назва → Enter» лишається; повтор — один селект.
- **Плюси:** найменше змін, той самий вигляд, знайомий користувачам. Усуває F2, U1, U2, U3.
- **Мінуси:** «Фіксована / Гнучка» лишаються технічними словами, і їх треба обирати ще до того, як людина подумала про час.
- **Складність:** M (≈ 2–3 дні з тестами).

### Варіант B — «Спершу час» (рухомість — властивість часу)

Вкладок рухомості немає. Є один блок **Коли**, а рухомість виводиться з того, що користувач вказав:

```
Назва *  [Спортзал__________________]
Коли     (Сьогодні)(Завтра)(Цього тижня)(Дата…)(🕘 Час…)(📥 На потім)
         ↳ обрано час 18:00–19:00:
           [🔒 Не переносити]  ← вимкнено = гнучка з бажаним часом
Тривалість (30)(60)(90)            Фаза (Будь-коли)(Вечір)
Повтор   [Не повторюється ▾]
```

- **Без часу** → гнучка (двигун шукає місце в межах дня, тижня чи фази).
- **З часом** → з'являється перемикач «🔒 Не переносити». Увімкнено — fixed, вимкнено — гнучка з бажаним часом. Fixed без часу неможливий, як і в домені.
- **Чотири комбінації:** час + замок + повтор. Видимих селекторів «типу» немає.
- **Швидкість:** найвища, бо типова дія — назва і, можливо, один чіп.
- **Плюси:** природна мова («коли»), найкраще для мобільного, близько до голосу.
- **Мінуси:** нова ментальна модель і більша переробка форми та e2e. Різниця між fixed і гнучкою з бажаним часом схована в одному перемикачі, тож треба перевірити, чи розуміють її звичайні користувачі. Стандарт для «зустріч о 10» — увімкнений замок? (продуктове рішення).
- **Складність:** L (≈ 5–7 днів, переписування `TaskForm`, `presetSwitch`, e2e).

### Варіант C — «Два явні перемикачі»

```
Як планувати   [ 📌 Точний час | ↔ Знайди час ]
Як часто       [ Один раз | 🔁 Повторюється ]
(кнопка внизу) [Зберегти на потім]
```

- Модель 1:1 з доменом, найпростіше пояснити й протестувати.
- **Мінуси:** два обов'язкові вибори ще до назви — повільніше захоплення. Бриф прямо застерігає від того, щоб показувати кожне поняття домену окремим селектором.
- **Складність:** M.

## 6. Рекомендація

**Варіант A**, з двома запозиченнями з B:
1. Усередині «Гнучкої» другорядні поля (бажаний час, дати) згорнуті під «Уточнити». Видимі лише назва, тривалість (чіпи) і фаза.
2. Блок «Повтор» однаковий в обох режимах і зберігається при перемиканні.

Чому:
- **Коректність:** прибирає F2 і модельні U1–U3 без нових понять. Разом із виправленнями F1, F3–F5 UI перестає обіцяти те, чого домен не робить.
- **Швидкість:** захоплення не гірше за поточне. Згортання в «Гнучкій» робить його швидшим.
- **Зрозумілість:** «Повтор» — властивість, як у Google Calendar чи Apple Calendar. Це загальновідомий патерн.
- **Сумісність:** той самий ряд чіпів, той самий `FixedSlotFields`, ті самі `filter-chip`. Редизайн не ламається.
- **Ризик:** B кращий для мобільного, але міняє ментальну модель і потребує перевірки на користувачах. Його варто розглядати окремо, і A цьому не заважає: блок «Повтор» і логіка payload будуть спільними.

### 7.2 Редагування

**Одноразова задача** — без змін: превʼю → «Редагувати» → повна форма.

**Повторення серії (клік по дню в календарі)** — превʼю показує:
`🔁 Щотижня пн, ср, пт · це повторення: ср 4 листоп.`

«Редагувати ▾»:

| Вибір | Що відкривається | Що можна змінити | Запит |
|---|---|---|---|
| **Лише цей день** | Шторка «Цей день»: час початку, тривалість (у межах дня) + кнопки «Пропустити» і «Видалити» | Лише час і тривалість. Під полями — рядок: «Назву, фазу й повтор можна змінити лише для всієї серії» | `move-event`, `seriesScope: occurrence` |
| **Цей і наступні** | Та сама шторка з підписом «з ср 4 листоп.» | Лише час і тривалість | `move-event`, `seriesScope: series` |
| **Усю серію** | Повна форма з банером «Зміни застосуються до всієї серії» | Усе | `PATCH /tasks/:id` |

Шторка «Цей день» — це наявний `MoveOccurrenceSheet` (у ньому вже є часова шкала з фазами і вільними вікнами) у новому режимі `occurrence`. Новий компонент не потрібен.

**Копія (перенесене повторення):** превʼю показує «Повторення серії «Спорт» за ср 4 листоп., перенесене». Редагування — як одноразової, але з F3: лише змінені поля, тож членство в серії не рветься.

**Повна форма серії:**
- «Коли» (fixed) → «Час» (год:хв і тривалість) окремо від «Починаючи з / До».
- Зміна рухомості (Фіксована ↔ Гнучка) зберігає повтор. Підтвердження потрібне лише тоді, коли гнучка серія без годинника стає фіксованою: «Вкажіть час — фіксована серія завжди в один і той самий час».
- Вимкнення повтору → діалог (§10, П5).

### 7.3 Перетягування

Без змін: зараз воно коректне (зонд → вибір scope → запис). Варто лише вирівняти тексти діалогу перетягування з меню «Редагувати».

## 10. Питання для продуктових рішень

1. **Типовий режим нової задачі** — Фіксована (як зараз за `task-creation-rules.md`) чи Гнучка? Для швидкого захоплення краще Гнучка (досить назви), для календарного користувача — Фіксована.
2. **«Лише цей день»:** чи вистачить часу й тривалості (бекенд уже вміє)? Чи потрібні також назва, нотатка, фаза для одного дня (потрібен новий бекенд, B1)?
3. **«Цей і наступні»** для полів, а не лише часу — потрібно? Потребує атомарного ендпоінта (B4).
4. **Відмітка «виконано» для одного повторення** (B2) — потрібна? Це найпомітніша відсутня можливість для звичок і рутин.
5. **Вимкнення повтору:** що лишається — найближче майбутнє повторення як одноразова задача, чи всі майбутні видаляються?
6. **Зміна тривалості серії:** лише нові повторення (поточна поведінка `keep`) чи всі майбутні (перезапис горизонту)?
7. **«Нагадування»** в одному ряду з режимами задачі — лишити? Це інша сутність, і при новій моделі ряд стає коротшим, тож воно не заважає.
8. **Перенесення повторення на інший день** (B3) — потрібне, чи обмеження «в межах дня» прийнятне?
9. **Варіант B** («спершу час») — розглянути як наступну ітерацію з тестом на користувачах?

Обмеження, що лишилися: день серії не переноситься на інший день (лише в межах дня); «цей і наступні» для серії без історії править усю серію (щоб не лишати порожню); у режимі e2e без Google сітка календаря порожня (дзеркало Google — єдине джерело карток), тому візуальна перевірка робилась із підміною `/calendar-providers/events`.
